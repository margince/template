# All-in-One Image — Design Specification

- **Date:** 2026-09-30.
- **Status:** Approved design (brainstorming session of 2026-09-30).
- **Extends:** [2026-09-24-client-instance-template-design.md](2026-09-24-client-instance-template-design.md), as its Section 9.9.

## 1. Background

A person who is not a developer and wants to try Margince has two options
today. The desktop folder runs without Docker, but it is built on macOS only
and each platform needs its own build. `make local-up` runs the release
images, but it needs a checkout, `make`, six containers, and ports 80 and 443.

This design adds a third option: one Docker image that contains all of
Margince, and one command that installs Docker when it is missing and starts
that image.

## 2. Goals

1. One image per instance release, `<repo>/all-in-one:<version>`, that runs
   the instance's Margince (core and its units) in one container.
2. A non-technical tester starts it with one pasted command on macOS,
   Windows, or Ubuntu. The command installs Docker when it is missing.
3. The container takes no configuration: no environment variable, no file,
   no flag. It needs a port and a volume.
4. The instance's own settings apply: the workspace from
   `deploy/production/config/margince.yaml`, and the demo dataset when the
   instance names one in `data.dataset` and the build can reach it.
5. `make` wraps every step for a person with a checkout. The `make` targets
   and the tester's command run the same scripts.

## 3. Non-Goals

- Production use. The image runs in test mode (`MARGINCE_ENV=test`) and
  never reads a license.
- HTTPS, and access from another computer. The port is published on
  `127.0.0.1` only.
- Upgrades of PostgreSQL across major versions inside the volume.
- Docker updates, and Windows on ARM.
- Changes to core. The image packages the role images that core's
  `Dockerfile` builds.

## 4. Decisions

| Topic | Decision |
|---|---|
| Audience | Non-technical testers. Developers use `make dev` and `make local-up`. |
| Image contents | The binaries and files of the `api`, `worker`, and `web` role images of the same version, plus PostgreSQL with pgvector, Redis, and nginx. |
| Base image | `pgvector/pgvector:pg16`, the PostgreSQL image that `make smoke` and the `host` adapter use. The Margince binaries are static (`CGO_ENABLED=0`), so they run on its Debian base. |
| Process supervision | `tini` as PID 1 and one start script, `margince-init`. It starts the processes in order and stops all of them when one exits; Docker's restart policy then restarts the container. |
| Mode | `MARGINCE_ENV=test`, fixed in the image. |
| Configuration | None from outside. Fixed values are in the image; generated values are in the volume. |
| Delivery to testers | A one-line command that downloads `install.sh` (macOS, Ubuntu) or `install.ps1` (Windows). |
| Delivery to developers | `make aio-*` targets that run the same scripts. |
| Image registry | The instance's `REGISTRY`, as for the role images. Testers pull without logging in, so the repository must allow anonymous pulls. |
| Admin password | Generated per installation and shown by the install command. |

## 5. The Image

### 5.1 Name and platforms

The image is `<repo>/all-in-one:<version>`, where `<repo>` is `image_repo`
(`<REGISTRY>/<name>`, or `<name>` without `REGISTRY`). A pushed image is built
for `linux/amd64` and `linux/arm64`. It carries the labels that `make package`
puts on the role images (`com.margince.instance.*`, `com.margince.core.*`)
and the OCI version and revision labels.

### 5.2 Contents

| Part | Source | Address inside the container |
|---|---|---|
| `margince-api`, `margince-migrate`, the api entrypoint | the `api` image | `:8080` |
| `margince-worker` | the `worker` image | none |
| The SPA | the `web` image (`/usr/share/nginx/html`) | served by nginx |
| nginx | Debian package, with the configuration in Section 5.4 | `:80`, the only published port |
| PostgreSQL 16 with `vector`, `unaccent`, `pg_trgm`, `btree_gist` | the base image | Unix socket `/run/postgresql` only |
| Redis | Debian package | `127.0.0.1:6379` |
| `margince-init`, `margince-logins` | `scripts/aio/` | none |
| `seed-demo` and the dataset | only when the build includes the dataset (Section 7.2) | none |
| The first-boot configuration | generated by `cli aio-config` (Section 7.1) | `/etc/margince/margince.yaml` |

### 5.3 Fixed settings

These values are set in the image and are the same for every installation:

| Setting | Value |
|---|---|
| `MARGINCE_ENV` | `test` |
| `MARGINCE_CONFIG` | `/etc/margince/margince.yaml` |
| `MARGINCE_OWNER_DSN` | `postgres://margince_owner@/margince?host=/run/postgresql` |
| `MARGINCE_DSN` | `postgres://margince_app@/margince?host=/run/postgresql` |
| `MARGINCE_REDIS` | `127.0.0.1:6379` |
| `MARGINCE_BLOBSTORE_PATH` | `/data/blobs` |

PostgreSQL accepts connections on its Unix socket only
(`listen_addresses = ''`), with `trust` authentication for local connections.
Nothing outside the container reaches the database. The owner and app roles
exist because core's migrations and the api need them. Their passwords are
random, used once by `db-bootstrap.sql`, and not stored.

### 5.4 nginx

nginx listens on port 80 and routes like the `host` adapter's Caddyfile:

| Path | Destination |
|---|---|
| `/healthz`, `/readyz`, `/metrics` and their subpaths | 404 |
| `/v1`, `/v1/*`, `/oauth/*`, `/mcp`, `/mcp/*`, `/.well-known/oauth-authorization-server*`, `/.well-known/oauth-protected-resource*`, `/webhooks/gmail`, `/webhooks/graph` | the api on `127.0.0.1:8080` |
| every other path | the SPA, with the caching and `Referrer-Policy` rules of core's `frontend/nginx.conf` |

### 5.5 The volume

One volume is mounted at `/data`:

| Path | Content | Owner |
|---|---|---|
| `/data/postgres` | the database cluster | `postgres` |
| `/data/redis` | Redis's append-only file | `redis` |
| `/data/blobs` | the file store | `app` (uid 10001) |
| `/data/secrets.env` | the generated keys and admin password, mode 600 | `root` |
| `/data/.seeded` | the marker of a completed seed | `root` |

Removing the container keeps the volume. Removing the volume resets Margince.

## 6. Start and Stop

`margince-init` runs as PID 1's child under `tini`.

### 6.1 First start

A start is a first start when `/data/secrets.env` does not exist.

1. Create `/data/secrets.env` (mode 600) with `MARGINCE_KEYVAULT_ROOT_KEY`
   (base64 of 32 random bytes), `MARGINCE_CONNECTOR_STATE_KEY` (hex of 32
   random bytes), `MARGINCE_WEBHOOK_KEY` (base64 of 32 random bytes), and
   `MARGINCE_ADMIN_PASSWORD` (24 random characters). These are the formats of
   `gen-env.sh instance`. The file is written to a temporary name and renamed,
   so an interrupted first start leaves no partial file.
2. Initialize the cluster in `/data/postgres`, start PostgreSQL, and run
   core's `db-bootstrap.sql` with two random role passwords.

### 6.2 Every start

1. Start PostgreSQL (when step 6.1.2 did not already start it) and wait
   until it accepts connections.
2. Start Redis and wait until it answers `PING`.
3. Start the api as the user `app`, with the fixed settings and the values of
   `/data/secrets.env` in its environment, through core's api entrypoint. The
   entrypoint migrates as the owner role and writes the bootstrap admin
   password file while the installation has no company.
4. Wait until `http://127.0.0.1:8080/readyz` answers 200, for at most 300
   seconds.
5. Start the worker as the user `app`, without the owner DSN and without the
   admin password.
6. Start nginx.
7. When the image carries the dataset and `/data/.seeded` does not exist,
   start the seed in the background (Section 7.3).

The values of `/data/secrets.env` reach only the api and the worker, through
their environment. No value appears on a command line or in the log.

### 6.3 Failure and stop

- When one process exits, `margince-init` stops the others in the reverse
  order and exits 1. The install command starts the container with
  `--restart unless-stopped`, so Docker starts it again.
- On `SIGTERM` (`docker stop`), `margince-init` stops nginx, the worker, the
  api, Redis, and PostgreSQL (fast shutdown), in that order, and exits 0.
- The image's `HEALTHCHECK` requests `http://127.0.0.1:8080/readyz` inside the
  container, so `docker ps` shows `healthy` when Margince is ready.

## 7. Build

### 7.1 First-boot configuration

`cli aio-config` (a new command of the Go CLI in `scripts/cli`) reads
`deploy/production/config/margince.yaml` and writes the image's
configuration:

- `bootstrap_admin.email` becomes `admin@localhost`, and
  `bootstrap_admin.password_file` becomes `secrets/admin-password` (the path
  core's api entrypoint writes).
- `mcp.connector_enabled` becomes `false`.
- `email` becomes `{enabled: false}`: a local trial has no mail relay, and an
  enabled relay makes the api require a public address.
- Every other key, `workspace` included, is kept.

When the file does not exist, it writes a default: the workspace name from
`display_name` in `instance.yaml`, `EUR`, `UTC`, and the values above.

### 7.2 `make aio VERSION=<v>`

1. Refuses a `VERSION` that is not a release version.
2. When a role image `<repo>/{api,web,worker}:<v>` is missing from the local
   image store, runs `make package VERSION=<v>`. With `PUSH=1` it uses the
   pushed role images instead and refuses without `REGISTRY`.
3. Assembles a build context in `build/aio/`: the files of `scripts/aio/`,
   the configuration from Section 7.1, and core's `db-bootstrap.sql`.
4. When `DATASET=<checkout>` is given: includes the dataset (the checkout
   without `.git/` and `tools/`) and builds `seed-demo` for `linux/amd64`
   and `linux/arm64` with the rule `make desktop-kit` uses. The demo dataset
   is euro-based, so a configuration whose `workspace.base_currency` is not
   `EUR` gets a notice and no dataset. Without `DATASET` the image has no
   dataset and the build prints a notice.
5. Runs `docker buildx build` and loads the image, or pushes it for both
   platforms with `PUSH=1`.

An image that includes the dataset contains the dataset's files. The guide
states this, so the instance owner chooses a registry that fits the dataset.

### 7.3 Seeding

The seed runs `seed-demo` against `http://127.0.0.1:8080` as
`admin@localhost`, with the owner DSN, the file store `/data/blobs`, and the
admin password from `/data/secrets.env`. When that password no longer signs
in, it uses the seeder's password `demo-password-123`, as the desktop loader
does. On success it creates `/data/.seeded`. On failure it logs the error,
Margince keeps running, and the next start tries again.

## 8. The Install Command

### 8.1 Scripts

`scripts/aio/install.sh` is POSIX `sh`, because `curl … | sh` runs it with
`sh`. `scripts/aio/install.ps1` is PowerShell 5.1 or later. Both take one
action: `up` (the default), `down`, `reset`, `logins`, or `logs`.

`make aio-scripts VERSION=<v>` writes both to `dist/aio/<v>/` with the image
reference, the container name `margince-<name>`, and the volume name
`margince-<name>-data` filled in. The release lane attaches them to the
GitHub release. The tester's command is:

| Platform | Command |
|---|---|
| macOS, Ubuntu | `curl -fsSL <url>/install.sh \| sh` |
| Windows | `irm <url>/install.ps1 \| iex` |

Another action is passed as `curl -fsSL <url>/install.sh | sh -s -- <action>`,
or on Windows by downloading the script and running
`.\install.ps1 -Action <action>`.

### 8.2 `up`

1. **Docker.** When `docker info` succeeds, continue at step 3.
2. **Install Docker, after the tester answers yes.** The question is read from
   the terminal, not from standard input, because standard input is the
   script. `--yes` answers it in advance.

   | System | Method |
   |---|---|
   | macOS | Docker Desktop: download `Docker.dmg` for the Mac's architecture, run its installer (`install --accept-license`, asks for the Mac password), start it. |
   | Windows | `winget install -e --id Docker.DockerDesktop`. When WSL 2 is missing, run `wsl --install --no-distribution` and ask the tester to restart and run the command again. |
   | Ubuntu 22.04, 24.04 | Docker Engine from Docker's apt repository, the method `make host-bootstrap` uses. Adds the user to the `docker` group and uses `sudo docker` for the rest of this run. |
   | any other system | Stop with the system's name and Docker's install page. |

3. **Wait** until `docker info` succeeds, for at most 180 seconds. On macOS
   and Windows the message says that Docker Desktop may ask to accept its
   terms.
4. **Image.** Pull the image when it is not in the local image store.
5. **Container.**

   | State | Action |
   |---|---|
   | no container | Create it (below). |
   | a container of another image | Remove it, keep the volume, and create it on the same port. |
   | a stopped container | Start it. |
   | a running container | Nothing. |

   The container is created with
   `docker run -d --name <container> --restart unless-stopped -p 127.0.0.1:<port>:80 -v <volume>:/data <image>`.
   `<port>` is 8080 when it is free, otherwise the first free port from 8081
   to 8099. A later run reads the port from `docker port`.
6. **Wait** until the container is `healthy`, for at most 600 seconds.
7. **Show** the address and the output of `margince-logins`, then open the
   browser.

### 8.3 Other actions

| Action | Effect |
|---|---|
| `down` | `docker stop <container>`. The data stays. |
| `reset` | After the tester types `yes`: remove the container and the volume. |
| `logins` | The address and the output of `margince-logins`. |
| `logs` | The last 200 lines of the container's log. |

`margince-logins` runs inside the container. It prints `admin@localhost` and
its password: the generated one, with the note that the first sign-in asks
for a new password, or `demo-password-123` when the installation is seeded.
In a seeded installation it also lists the demo colleagues and their
password `1234`, as `make desktop-logins` does.

### 8.4 Messages

Every failure names what to do next, for example:

- `Docker is installed but not running. Start Docker Desktop, then run this command again.`
- `Ports 8080 to 8099 are all in use. Close a program that uses one of them, then run this command again.`
- `Margince did not start within 10 minutes. Run the command again with "logs" and send the output to the person who gave you this command.`

## 9. `make` Targets

| Target | Runs |
|---|---|
| `make aio VERSION=<v>` | Section 7.2 (`DATASET=`, `PUSH=1`, `REGISTRY=`). |
| `make aio-up VERSION=<v>` | `install.sh up` with the local image. |
| `make aio-down` | `install.sh down`. |
| `make aio-reset` | `install.sh reset`. |
| `make aio-logins` | `install.sh logins`. |
| `make aio-logs` | `install.sh logs`. |
| `make aio-smoke VERSION=<v>` | Section 10.3. |
| `make aio-scripts VERSION=<v>` | Section 8.1. |

`scripts/aio.sh` implements `aio`, `aio-smoke`, and `aio-scripts`, with the
functions of `scripts/lib.sh`.

## 10. Testing

### 10.1 `scripts/aio.test.sh`

With a stub `docker`: `make aio` refuses a non-release version, runs
`make package` only for missing role images, passes the image names and
labels to the build, refuses `PUSH=1` without `REGISTRY`, and includes the
dataset only with `DATASET` and a `EUR` workspace. `aio-scripts` fills in
every placeholder.

### 10.2 `scripts/aio-install.test.sh` and `scripts/aio-install.test.ps1`

`install.sh` with stubs for `docker`, `uname`, `/etc/os-release`, `curl`,
`sudo`, and the terminal: the install method per system, the refusal of an
unsupported system, no install when Docker works, no install without a yes,
the port choice, the replacement of a container of another image with the
volume kept, and each action. No stub records a secret on a command line.
`install.ps1` gets the same cases with stubbed commands; the test runs where
`pwsh` is installed, and in CI.

### 10.3 `make aio-smoke VERSION=<v>`

With the real image and a temporary volume and container name: the first
start reaches `healthy`, `admin@localhost` signs in with the generated
password through nginx, `/` serves the SPA, `/readyz` answers 404 through
nginx, a restart keeps the data, and everything is removed at the end, also
on failure. `release.yml` runs it on `linux/amd64`.

### 10.4 Go

`cli aio-config`: the overrides, the kept keys, and the default without a
file.

## 11. Release

The `images` job of `release.yml`:

1. After `make smoke`, runs `make aio VERSION=<v>` and
   `make aio-smoke VERSION=<v>` on the loaded `linux/amd64` images.
2. When `REGISTRY` is set, after the role images are pushed, runs
   `make aio VERSION=<v> PUSH=1` and adds the image to the image list.
3. Runs `make aio-scripts VERSION=<v>` and uploads `dist/aio/<v>/` as an
   artifact.

The dataset reaches the job as it reaches the desktop lane:
`DATASET_REPOSITORY` and `DATASET_DEPLOY_KEY`. The `publish` job attaches
`install.sh` and `install.ps1` to the release and adds the tester's commands
to the release notes.

## 13. Rejected Alternatives

| Alternative | Reason for rejection |
|---|---|
| A Linux desktop folder in a container | Core has no Linux desktop build; PostgreSQL and pgvector would have to be built for Linux in core first. |
| The install command runs the role images with Compose | Not one image; it needs ports 80 and 443 and shows a certificate warning. |
| `s6-overlay` as supervisor | A third-party download with pinned checksums per architecture. A container restart covers a failed process for a trial. |
| A fixed admin password | A known password in a public image. |
| Fixed keys in the image | The image is public, so every tester's sealed credentials would be readable. |
| `make` as the tester's command | Windows has no `make`, and on macOS `make` starts the installation of the Xcode Command Line Tools. |
